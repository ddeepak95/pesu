# Phase 2 — AI Usage Metering: Counters + Reconcile + Runtime Backstops

Companion implementation plan for `dev-docs/ai-usage-metering-plan.md` §9 point 2. That doc remains the source of truth for the overall design and revision history; this file is the concrete, sequenced implementation plan for Phase 2 specifically, written after exploring the actual Phase-1 code on `usage-metering` (not derived from the plan doc's prose alone — every file:line reference below was verified against the real code this session).

## Context

Phase 1 (gateway inversion, always-on `ai_invocations` capture, rate card, build-gated exhaustiveness checks) shipped earlier this session and is live on `usage-metering`. Phase 2 closes three remaining gaps before any wallet/enforcement work (Phase 3) can be trusted:

1. **No rollup table.** Every "how much has institution X spent" question today means scanning `ai_invocations` directly — no O(1) analytics read exists yet (`ai_usage_counters`, §4.5, doesn't exist in code).
2. **No drift/health check.** Nothing catches a silently-failed write, a null-cost row (unpriced model), an unattributed row, or a request that crashed mid-flight and got stuck `pending` forever.
3. **No runtime backstop.** `src/lib/ai/gateway/context.ts` is a stub — attribution (`userId` especially: confirmed **0 of 8** current call sites set it) relies entirely on each route remembering to pass it explicitly, with no ambient fallback and no fail-closed detection if one is missed. There's also no transport-layer catch-all if some future SDK surface bypasses the normal `startAiInvocation`/`completeAiInvocation` funnel.

Two architectural decisions were confirmed with the user before this plan was written:
- **Scheduling: `pg_cron`**, not Vercel Cron. This repo has zero cron infra today (no `pg_cron`/`pg_net` extension, no `vercel.json`, no GitHub Actions, no Supabase Edge Functions — verified via migration grep). The nightly reconcile job is pure SQL aggregation with no external API calls, and Phase 3 will need the same pattern again for its monthly credit-grant job — `pg_cron` avoids ever wrapping a growing full-table aggregation in an HTTP request with a timeout ceiling.
- **Runtime backstops: ALS ambient context ships this phase; the instrumented-fetch transport-layer catch-all is deferred.** (Revised from the original "full §7.4 scope, not deferring either part" — see D3 for why a build-gated check replaces it as the primary control.)

## Design decisions

**D1 — `key_owner` is derived in SQL at aggregation time, never persisted.** `ai_invocations.ai_key_source` (`"platform" | "institution" | "class" | "env" | "unconfigured"`) already exists and is written at insert (`recordInvocation.ts:210`). Rather than adding a new `key_owner` column that could drift from `ai_key_source`, a single SQL function `public.key_owner_from_source(text) returns text` (`platform`/`env` → `'platform'`; `institution`/`class` → `'byok'`; anything else → `'platform'` fail-safe, flagged separately by the reconcile job) is the one source of truth, called by both the hot-path upsert and the nightly rebuild. This matches §4.5's framing of counters as "a pure cache... rebuildable by re-aggregating the base table."

**D2 — the counter upsert is awaited, isolated from the caller's failure, with retries deferred to `after()`.** (Revised from an earlier fire-and-forget draft — see reasoning below.) `completeAiInvocation` is already on the response-blocking path for two of three funnels (`structured.ts:88` generateText, and STT/TTS synthesis) — confirmed by reading `recordInvocation.ts` in full. The first `record_usage_counter` attempt is `await`ed inline, wrapped in a `try/catch` that logs to `app_logs` on failure but never rethrows — so a counter failure can never fail the user's AI response, but the code path is guaranteed to observe and log every failure (unlike a detached `void` promise, which can be silently killed by the serverless runtime once the response is sent, with no guarantee its own error handler ever runs). If the first attempt fails, retries (short backoff, e.g. 200ms/1s/3s) are pushed into an `after()` callback — since that only runs after the response has already been sent, retries add zero latency to the user-facing call. Final exhaustion after retries logs an `error`-level `app_logs` row and is left to the nightly reconcile's full rebuild as the last-resort backstop.

Rejected alternatives, for the record:
- **Pure fire-and-forget (`void service.rpc(...).catch(...)`, never awaited at all):** adds zero latency, but a detached promise isn't guaranteed to run to completion once the response is sent on a serverless runtime (this app uses `next/server`'s `after()` elsewhere — `turn/route.ts:1000` — for exactly this class of problem), and worse, the failure-logging lives inside that same at-risk continuation, so the safety net and the thing it's meant to catch can both be lost silently together.
- **A Postgres trigger on `ai_invocations` (`AFTER UPDATE`) instead of an app-level call:** would guarantee atomicity with the main write, but couples the cache table's correctness to the source-of-truth write's success (a bug or lock contention in `record_usage_counter` could roll back the actual billing row), and risks re-firing on unrelated later updates to an already-completed row (e.g. `linkInvocationToChatMessage` at `recordInvocation.ts:462-478`) unless the trigger's `WHEN` clause precisely guards the `status` transition. Rejected in favor of keeping the cache write fully isolated from the source-of-truth write, per §4.5's "counters are a pure, rebuildable cache" framing.
- **Latency tradeoff accepted because it's proportionally negligible:** the metered operations are LLM/STT/TTS calls (hundreds of ms to several seconds); one small indexed 4-row upsert (same shape as the `select ai_model_id, usage_type` round-trip already awaited a few lines earlier in `completeAiInvocation`) is noise by comparison. Watch point: the counters row for a given `(institution, class, key_owner, period, usage_type)` is a hot row under concurrency — if a popular institution's completions cluster in time, the awaited upsert could occasionally queue behind that row's lock. Not a concern at current scale; revisit (e.g. move to the Tier-3-style transactional outbox pattern — append a cheap, non-contending event row in the same transaction as the main write, drained by a separate frequent `pg_cron` job) if p99 latency or lock-wait metrics ever show this as a real hot spot.

**D3 — funnel coverage is enforced at build time via an explicit call-site registry, not by a runtime instrumented-fetch backstop.** (Revised — see reasoning below.) Every legitimate provider call already runs inside a `startAiInvocation`/`completeAiInvocation` bracket, issued from a small, closed set of files: the import boundary (`assertGatewayImportBoundaryHolds`, already live) confines every AI SDK import and every speech-provider import to `src/lib/ai/gateway/**`, so "a future call escapes the funnel" can really only happen by someone adding a new call site inside those already-confined files and forgetting to bracket it — not from some arbitrary file elsewhere in the app.

That means the realistic risk is a static, source-level property, not something that needs live network traffic to detect. `assertFunnelCoverageComplete()` (new, `src/lib/ai/metering/validate.ts`, same idiom as `assertCatalogUsageTypesComplete`/`assertGatewayImportBoundaryHolds`) scans every file in `src/lib/ai/gateway/**` for recognizable AI-call patterns (`generateText(`, `streamObject(`, the speech-provider client/fetch call shapes) and checks each occurrence against an explicit registry of known, accounted-for call sites (file + call description — the same list this doc already enumerated: `structured.ts:88`, `turnStream.ts:170`, each `speech.ts` provider call). Any call-shape match not in the registry fails the build with a message telling the developer to add it to the registry and confirm it's wired through `startAiInvocation`/`completeAiInvocation`. Enforced at `npm run validate:ai-metering` (prebuild), same as the other exhaustiveness checks — no ALS marker, no runtime detection, no per-request overhead.

Rejected/deferred alternative — the instrumented-fetch + ALS "funnel marker" backstop (original draft): wraps the real `fetch` and flags any call made while a second ALS marker is unset. Two problems made this a poor *primary* control: (1) the marker only proves "some funnel bracket was open somewhere in the async chain," not "this exact fetch is the one that bracket meant to cover" — it silently trusts the one-call-per-bracket assumption rather than verifying it; (2) it's the highest-file-touch, most invasive part of Phase 2 (threading `fetchImpl` through `provider.ts`, 4 speech provider files, the OpenAI client singleton) for a risk the build-gated registry now catches earlier and more cheaply. It does retain one residual value the registry can't cover — catching a call that truly never produces an `ai_invocations` row at all (an unknown-unknown call shape, or an AsyncLocalStorage-continuity bug in a correctly-wrapped call) is invisible to both the registry (a source-level check, which assumes the pattern is recognizable) and the nightly reconcile (which only aggregates rows that already exist). That residual risk is accepted as a documented gap for now; revisit instrumented-fetch as a later addition only if a new provider-integration pattern or an ALS-continuity incident is actually observed, rather than building it preemptively.

**WebSocket sessions (Cartesia/Sarvam TTS) remain outside any transport-layer backstop** — they never call `fetch`, so neither the registry check nor a hypothetical instrumented-fetch would see them. Their existing self-metering bracket in `speech.ts` is covered by the reconcile job's `stuck_pending_rows` anomaly flag (§2): a WS session that opens a bracket and never calls `completeAiInvocation` shows up as a stuck `pending` row after 60 minutes. That check was already planned for crash detection; it doubles as the WS funnel-coverage backstop, so no new work is needed for this gap.

**D4 — ALS context carries only `userId` and `classId`; `institutionId` is dropped.** `persistAiInvocationStart` already authoritatively resolves `institution_id` from `classId` via `resolveInstitutionId` (`recordInvocation.ts:198-200`), and all 8 current call sites always know `classId` — so `institutionId` would be dead, untested weight on `AiRequestContext` (no call site would ever populate or read it). It's left out of the type now; add it back, with a real call site to exercise it, if a future platform-scope route with no `classId` ever needs it. What ALS actually fixes today: **`user_id` is currently always `null`** on every row from these 8 routes (none of them call `supabase.auth.getUser()` before invoking the gateway), and there is currently zero detection if a future call site forgets to pass context entirely.

## Implementation

### 1. Migration — `ai_usage_counters` + `record_usage_counter()`

New file `supabase/migrations/20260714000000_ai_usage_counters.sql`:
- `ai_usage_counters` table: `institution_id uuid not null references institutions(id)`, `class_id uuid not null default '00000000...0000'` (sentinel for institution-wide rows — deliberately no FK, matching §4.5's rationale), `key_owner text not null`, `period_start date not null`, `usage_type text not null` (or `'all'`), `credits numeric(20,8) not null default 0`, `events bigint not null default 0`, `updated_at timestamptz not null default now()`. PK `(institution_id, class_id, key_owner, period_start, usage_type)`.
- RLS: SELECT policy mirrors the existing `ai_invocations` policy (`supabase/migrations/20260713000000_ai_invocations_metering.sql:50-55`) — super admin, institution admin, or class teacher/admin (using the existing `is_platform_super_admin()`/`is_institution_admin()`/`is_class_teacher_admin()` helpers, confirmed present in the migrations). No write policies — service-role only, same convention as `ai_invocations`/`app_logs`.
- `public.key_owner_from_source(text) returns text` — the D1 mapping, `language sql immutable`.
- `public.record_usage_counter(p_institution_id uuid, p_class_id uuid, p_ai_key_source text, p_started_at timestamptz, p_usage_type text, p_credits numeric) returns void` — `security definer` plpgsql. Computes `period_start` as UTC calendar-month start (matches plan §10 decision #6), calls `key_owner_from_source`, and upserts **4 rows** via a `values (...) cross join`-style fan-out: `(inst, class, usage_type)`, `(inst, class, 'all')`, `(inst, SENTINEL, usage_type)`, `(inst, SENTINEL, 'all')`, each `on conflict ... do update set credits = credits + excluded.credits, events = events + 1`. No-ops (returns early) if `p_institution_id` is null.
- `revoke execute ... from anon, authenticated` on both functions.

*Verify:* apply the migration, then manually call `record_usage_counter` twice with the same args in the SQL editor — confirm the first call produces 4 rows and the second accumulates (`credits`/`events` both increase) rather than overwriting.

### 2. Migration — `pg_cron` + nightly reconcile

New file `supabase/migrations/20260714010000_pg_cron_usage_reconcile.sql`:
- `create extension if not exists pg_cron with schema extensions;` (flag: if this fails on Supabase due to platform permissions, enable it once via Dashboard → Database → Extensions, then re-run — the rest of the migration still applies).
- `public.reconcile_ai_usage_counters(p_since date default null) returns void` — `security definer` plpgsql, does, in order:
  1. Computes `v_cutoff := coalesce(p_since, date_trunc('month', now()) - interval '1 day')`. `ai_usage_counters.period_start` buckets by UTC calendar month (§1), and a closed month's rows never change again once that month ends — so the default rolling window only needs to cover the current period plus a 1-day buffer into the previous one (same buffer logic as the anomaly window below, for calls that land right at a month boundary). `p_since` is a manual escape hatch for the rare real backfill (a months-old row gets corrected) — the automatic nightly schedule always calls with the default.
  2. Snapshots sentinel totals (`class_id` sentinel, `usage_type='all'`) for periods `>= v_cutoff` into a temp table.
  3. **Windowed rebuild**: `delete from ai_usage_counters where period_start >= v_cutoff`, then re-`insert...select...group by` from `ai_invocations` (where `started_at >= v_cutoff and status='completed' and credits is not null and institution_id is not null`), using `key_owner_from_source` for consistency with the hot path. Still a from-scratch recompute-from-source rather than incremental diffing — keeping §4.5's "eliminates a class of diff bugs" property — but bounded to the one or two periods that can plausibly still be in flux, instead of re-deriving every already-settled month on every run. Cost stays roughly constant as `ai_invocations` grows into years of history. Both steps run inside one function invocation so no reader observes a gap.
  4. **Drift check**: compares the pre-rebuild snapshot to the freshly rebuilt sentinel totals (same `>= v_cutoff` scope); any institution/key_owner pair that moved by more than $0.01 worth of credits gets a `warn`-level `app_logs` row (`event: 'counter_drift'`) — this is the signal that the per-invocation upsert (§3) exhausted its `after()` retries and silently failed at least once since the last run (D2's "last-resort backstop").
  5. **Anomaly flags**, each an `app_logs` insert when count > 0: `null_cost_rows` (completed, `cost_usd is null`, last 2 days), `unattributed_rows` (`app_function_key = 'unattributed'`, last 2 days — the ALS fail-closed prod-degrade signal), `unmapped_key_source` (`ai_key_source` outside the 4 known values, last 2 days — flags D1's fail-safe default firing).
  6. **Stuck pending — alert, then close**: `stuck_pending_rows` still flags any row `status='pending'` older than 60 minutes (`app_logs` warning — "something's probably wrong, go look"), unchanged. New: rows still `pending` past **24 hours** are auto-closed — `update ai_invocations set status='failed' where status='pending' and started_at < now() - interval '24 hours'` — plus an `app_logs` `event: 'reconcile_closed_stuck_pending'` row (count + ids), distinguishing this from a normally-caught runtime failure. Needed because every gateway call site already wraps its provider call in try/catch and always resolves to `completed`/`failed` on any thrown error (confirmed in `structured.ts`/`speech.ts`) — a row can only get stuck at `pending` if the whole process was killed mid-request (function timeout, OOM, deploy restart), so nothing else will ever close it. Without this, the same dead row re-fires the 60-minute alert every night, forever. 24h is comfortably past any legitimate in-flight call or transient platform hiccup, so it's safe to treat as terminal.
- `select cron.schedule('ai-usage-counters-nightly-reconcile', '0 8 * * *', $$ select public.reconcile_ai_usage_counters(); $$);` — daily 08:00 UTC (low-traffic window for a US-institution-heavy base); revisit once real traffic is observed.

*Verify:* manually `select public.reconcile_ai_usage_counters();`, confirm `ai_usage_counters` repopulates and `select * from cron.job;` shows the schedule. Deliberately backdate one row's `started_at` and insert one `app_function_key='unattributed'` row to confirm both anomaly flags fire in `app_logs` on the next manual call. Additionally: insert (or manually preserve) a counters row for a closed prior period, run the reconcile, and confirm it's untouched (proves the window, not a full truncate); insert a row with `status='pending'` and `started_at` 25 hours in the past, run reconcile, and confirm it flips to `failed` with the `reconcile_closed_stuck_pending` log row.

**Deferred — alert dispatch, not built this phase.** Today, `warn`/`error` `app_logs` rows are only ever surfaced by an admin reading the table directly (RLS-gated, per `ai-retry-and-failure-recovery-plan.md` §8) — nothing pushes them anywhere. No push path is needed yet, and nothing above is designed to require one: `app_logs` is already a stable, source-agnostic detection surface, so adding push alerts later is purely additive, not a redesign. When it's needed: a separate `pg_cron` job (`dispatch_app_log_alerts()`, e.g. every 5–15 min) selects `warn`/`error` rows where a new nullable `app_logs.notified_at` column is still null, `net.http_post`s them as a batch to an internal app API route (auth'd via a shared secret, e.g. Supabase Vault), which then fans out to Slack/email/etc. using the app's existing secrets management — deliberately routed through the app rather than a raw webhook URL in SQL, so "where alerts go" lives in one place. `notified_at` is intentionally not added now — it would sit unused until a dispatcher exists to set it. Rejected for now: bundling alerting directly into `reconcile_ai_usage_counters()` (Option A) — would work, but means every future anomaly-producing job (Phase 3's monthly credit-grant reconcile) re-implements its own HTTP-dispatch logic instead of reusing one dispatcher keyed off `app_logs`.

### 3. `recordInvocation.ts` wiring

Both changes in `src/lib/ai/logging/recordInvocation.ts`:
- **`completeAiInvocation`**: extend the existing re-read at line 307-311 from `.select("ai_model_id, usage_type")` to also select `ai_key_source, institution_id, class_id, started_at` (one extra round-trip is already happening there — no new query). After the `.update()` at line 383-403 succeeds and `computed.credits != null`, call a small `upsertUsageCounter(rpcArgs)` helper: `await service.rpc("record_usage_counter", rpcArgs)`, wrapped in `try/catch`, logging an `app_logs` `warn` (`event: "counter_upsert_failed"`) on either an `error` result or a thrown exception — never rethrown, so a counter failure can't fail `completeAiInvocation`. If that first attempt fails, register `after(async () => { for (const delayMs of [200, 1000, 3000]) { await sleep(delayMs); if (await upsertUsageCounter(rpcArgs)) return; } logAppEvent({ level: "error", ..., event: "counter_upsert_exhausted" }); })` — retries cost zero response latency since they run after the response is sent. Per D2.
- **`persistAiInvocationStart`** (lines 190-241): read ambient context via the new `getAiContext()` (§4 below); resolve `userId`/`classId` as `input.X ?? ambient?.X ?? null`. If nothing resolves at all (`ambient === undefined && classId == null && userId == null`): in non-production, `throw new AiContextMissingError(...)`; in production, insert with `app_function_key: "unattributed"` (widened to `string` locally — no DB constraint blocks this) and log an `error`-level `app_logs` row (`event: 'ai_context_missing'`). `institution_id` resolution stays exactly as-is (`resolveInstitutionId` from `classId`, line 198-200) — per D4, `AiRequestContext` carries no `institutionId` field at all.

*Verify:* run one real AI request locally, confirm `ai_usage_counters` gets 4 new/incremented rows matching the `ai_invocations` row's `credits`, and confirm the added response latency is small/bounded (single indexed upsert, comparable to the existing re-read round-trip). Then simulate a failure (e.g. temporarily point `record_usage_counter` at a bad arg) and confirm: the response still succeeds, a `counter_upsert_failed` row appears in `app_logs` immediately, and the `after()` retry loop attempts up to 3 times before logging `counter_upsert_exhausted`.

## Sequencing

1. **Counters migration** (§1) — purely additive SQL, zero call sites touched, safe to ship idle.
2. **`recordInvocation.ts` RPC wiring** (§3, counter half only) — small isolated diff, depends on step 1.
3. **Reconcile migration** (§2) — depends on step 1's schema; landing after step 2 means its first drift check has real live data instead of an empty table.
4. **ALS context** (§3 fail-closed half + §4) — land together as one unit (the fail-closed check is meaningless without `context.ts`, and the wraps are meaningless without something reading them). Land after 1-3 are proven stable in isolation, since this is the highest-risk step (8 route files touched, adds a dev-mode throw).
5. **Funnel-coverage build check** (§5) — pure static analysis, no runtime dependency on any other step; could ship anytime, but sequenced last here since it's the lowest-risk step and easiest to bisect if the pattern-matching turns out too strict/loose against real call sites.

Every step ships in a state where the app is fully functional — nothing depends on a later step to be safe in production.

## Verification (every step)

No test runner/CI in this repo. After each step: `npx tsc --noEmit`, `npm run lint`, `npm run validate:ai-metering`, `npm run build`. Per-step manual/SQL verification is detailed inline above.
